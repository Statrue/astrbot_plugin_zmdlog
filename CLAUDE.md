# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

AstrBot plugin (`ZmdLogBot`) that queries public ZMDLogs data (Endfield DPS leaderboards, account best records, battle reports) and replies with a single 1280px-wide PNG rendered by Jinja2 + Playwright. Entry point is `main.py` (`ZmdLogBotPlugin(Star)`); all logic lives in `core/`. Python 3.10+, deps in `requirements.txt` (httpx, jinja2, playwright, pypinyin). Chromium must be installed separately (`python -m playwright install chromium`).

## Commands

```bash
.venv/Scripts/python.exe -m unittest discover -s tests -v          # full suite (~250 tests, ~18s)
.venv/Scripts/python.exe -m ruff check main.py core tests tools    # lint (ruff.toml: E/F/I/W, py310)
.venv/Scripts/python.exe -m unittest tests.test_matcher -v         # one module
.venv/Scripts/python.exe -m unittest tests.test_matcher.MatcherTests.test_slug_and_board_aliases_match_one_board
```

Tests import `core.*` directly (run from repo root). Playwright is *not* exercised by tests — render tests only cover template output and validation logic. Lint with ruff (`ruff.toml`); `ruff format` is not enforced on the existing files. Runtime is inside AstrBot (`data/plugins/astrbot_plugin_zmdlog`); keep `core/` free of AstrBot imports so it stays unit-testable. AstrBot itself is installed in `.venv`, so `main.py` *can* be driven: `tests/test_main_handlers.py` imports it as the package `astrbot_plugin_zmdlog.main` (repo parent on `sys.path`), sets `main.StarTools = None` so nothing touches the real data dir, and feeds it fake events/clients/renderers — it is skipped wherever AstrBot is absent. Two traps when writing such tests: exceptions must come from `astrbot_plugin_zmdlog.core.*` (the package's class identities, which `main.py` catches), not from `core.*`; and merely importing `astrbot.api` creates a `./data` directory in the CWD (gitignored).

## Architecture (request flow)

`main.py` → `core/routing.parse_zmdlog_payload` (subcommand + trailing `--top` / `--角色` / `--范围` / `--潜能` options, parsed by `_extract_options`; each route rejects options it does not accept) → `_dispatch`:
- HELP → `core/help.build_help_page` (local only, no API)
- BATTLE_QUERY with a non-reference argument falls through to the board-only pipeline as `CandidateView.BATTLE` (routing pre-splits a trailing rank token — `战报 罗丹 3` / `第3` / `#3`, default 1, stored as `RouteRequest.battle_rank`); `_render_board` picks the ranking row with that rank and renders its battle summary. LOADOUT_QUERY (`配装`, alias `装备`) and SKILL_QUERY (`技能`, alias `技能统计`) take the identical argument shape (`routing._BATTLE_STYLE_COMMANDS`) and share the whole lookup (`main._BATTLE_STYLE_ROUTES` / `_BATTLE_VIEWS`, `CandidateView.LOADOUT|SKILLS`); only `main._render_battle_view` differs, drawing the loadout or skills page and answering in text (`_NO_LOADOUT_MESSAGE` / `_NO_SKILL_STATS_MESSAGE`) when an older upload carries no roster or no `roleSkillStats`. The battle card itself ends with a 阵容与配装 section (per-slot Lv / 潜能 / 精炼 / suit lines + top-3 damage sources). `core/loadout.py` is the pure layer: skill display names and categories mirror upstream `apps/web/lib/format/skill-display.ts` (plus 机制 / 套装 / 武器 buckets for `buff_*` keys), `group_skill_damage` folds the A1–A5 normal-attack chain and same-name rows (three "终结技" sub-hits) into one row, `infer_suit_names` reads the suit of an unnamed piece (upstream falls back to the raw item id as `pieceName`) off a named sibling in the same battle via the item-id token, `skill_level_summary` picks 普攻/战技/连携/终结 levels by key suffix. Templates: `resources/loadout/`, `resources/skills/`, shared `resources/common/loadout.css`; weapon / equip icons are site-relative like avatars, and when upstream omits `iconUrl` (its catalog does not know the piece yet, while the file exists) `presentation._derived_asset_url` builds the conventional `/images/equip/iconbig/{itemId}.png` / `/images/weapon/icon/{weaponTemplate}.png` path, which the template's `onerror` drops if wrong. TIMELINE_QUERY (`技能轴`, aliases `排轴` / `时间轴`) takes the same argument shape but reads the public export (`client.get_battle_export`, own `battle_export_cache`) instead of the battle detail: `_render_battle_view` takes the battle *id* and fetches whichever payload the view needs, and answers a 422 `battle_export_unsupported` (upload too old to carry casts) or a 429 in text (`_NO_TIMELINE_MESSAGE` / `_TIMELINE_RATE_LIMITED_MESSAGE`) right there, so every route that reaches a battle gets the same wording. `core/timeline.py` is pure: `classify_cast` applies name rules, then *end-anchored* key rules ported from upstream `apps/web/lib/endaxis-project.ts` — a mechanism entity such as `…_combo_skill_water_gene` must not be drawn as the player's 连携技 (upstream's own "汤汤 连携×3" incident) — and hides movement noise (dodge / dash / sprint / idle / born / die / hitstop / switch, `plunging_attack_end`); `build_timeline` drops pre-timer casts, clips casts past `durationMs` and **folds bursts** per lane (`_fold`: consecutive normal-attack segments within `MERGE_GAP_MS` become one 普攻 run, the same move fired again within the gap becomes one event with a count; summon-sourced casts, `skillSource == "Summon"`, form a second stream). **The chart is a vertical rail** (`resources/common/timeline-rail.html` macro + `resources/common/timeline.css`, shared by the battle card's 施法节奏 section and the 技能轴 page) built on one rule from the user's design memo: 线管连续、长度管时长、宽度与颜色管招式层级、节点管瞬时. Time runs down; every character has a 2 px idle rail line at `_RAIL_X_PX`; each folded event with a known end is a bar growing rightwards from the line, as tall as it lasts (min 5 px) and as wide as its kind matters (`_RAIL_BAR_PX`: 普攻 8, 其他 12, 战技/连携/重击 16, 终结技 20, the last with a diamond landmark); an instant is a 7 px dot (diamond for a 终结技); own moves that overlap step right into further columns (`_rail_columns`, `_RAIL_COLUMN_STEP_PX`) and the lane's labels move with them (`RailLaneView.label_left`); summons keep to an 8 px hatched strip left of the line; a heavy that recovers energy gets a yellow dot. Labels (`time · name ×n`) start at `_RAIL_LABEL_LEFT_PX`, slide down when neighbours are closer than one 15 px line, are dropped past a per-category slack (an ultimate never), and a narrow bar gets a hairline leader to its label while the label is still level with it. `build_timeline_view` picks the scale per host: the card targets ≈ 560 px (6–24 px/s), the page ≈ 1600 px (10–40 px/s); the tick step is the first of 1/2/5/10/30/60 s that is ≥ 34 px apart. Four layouts came before this one and must not come back: horizontal 20-second strips (the fixed 1280 px width could not fit a name into a half-second cast), full-width vertical blocks ("一整块砸下来"), a hairline rail with dots (too thin to read without zooming), and a uniform 44 px track (the light-grey normal-attack runs read as columns of filler); the user's memo of 2026-09-03 settled the graded widths. Portraits use the observed `/images/character/charremoteicon/icon_{key}.png` convention because the export has no avatar URLs; the `<img onerror>` drops a wrong guess. The battle card fetches the export best-effort (`main._battle_export_for_card`: 422 / 429 become a one-line note, anything else silently omits the section), so 战报 and the auto-expand path never fail because the export did
- COMPARE_QUERY (`对比`, alias `比较`) → `routing._parse_compare`: two reference-shaped tokens (link / `btl_*`) become `query` + `compare_target` and skip the board lookup; otherwise up to two ranks are read off the tail (`battle_rank`, `compare_rank`; none ⇒ 1 vs 2, one ⇒ 1 vs it, equal ⇒ error) and the keyword goes through the board-only pipeline as `CandidateView.COMPARE` (`PendingCandidates.compare_rank` travels with the pick list; `_render_board` resolves both ranks and names the first missing one). `main._render_compare` fetches both details concurrently (same id ⇒ text; different `boss_name` ⇒ text, because every boss has its own rotation and the user ruled cross-boss comparison meaningless) and `presentation.build_compare_page` builds the two `BattlePage`s the card would draw and composes them: facts with the better side marked (time lower, DPS / damage higher; deltas as seconds / percent of the lower side), the roster union in A's order with absent sides marked, both *team* DPS lines on one shared axis (`_compare_curve`: the shorter fight's line simply stops, dashed end markers), and per character the gear lines (`_gear_lines`: 等级·潜能, 武器·精炼, four pieces by compact suit label, skill levels) with differing lines flagged plus each side's top-3 damage sources. Template `resources/compare/`; A is yellow and B blue throughout. The 技能轴 page also fetches the detail best-effort (`_battle_detail_if_available`) only to add the BUFF 覆盖 band above its rail.
- ALL_RANKINGS → `hot-bosses` cache → all-top3 template
- The battle card carries two more charts built from the same response by `core/telemetry.py` (pure) and `presentation.build_dps_curve_view` / `build_buff_band_view`, both `None` when the upload has no telemetry: **DPS 曲线** buckets damage per second and divides the running total by elapsed time (the board's own reading, so each line ends at that character's DPS in the table above; the line colour is the participant's `share-seg--N` index, and the team line is included in the axis peak or it would clip flat), and **BUFF 覆盖**, its own section directly under the curve: one row per buff keyed by (name, effect, source) so upstream's caster / owner / weapon-tag variants of one buff merge into a single uptime row, applications within `TEAM_MERGE_GAP_MS` (80 ms) fold into one span, overlapping refreshes merge, only damage zones (`atk` / `dmg_inc` / `amp` / `combo`) qualify, and rows past `MAX_BUFF_ROWS` (12) are counted in a note. Both live in `resources/common/battle-charts.{html,css}` and share one three-column skeleton (`.hchart-row`: 232 px side | track | 40 px gutter) and one tick set (`_horizontal_ticks`), so their time axes line up and a buff bar can be read against the curve above it; the curve's legend therefore sits in the left column, not under the plot. The section order is DPS 曲线 → BUFF 覆盖 → 施法节奏 so the one switch from left-to-right to top-to-bottom time coincides with a heading (the band was first placed inside the 施法节奏 section and the user asked for it to be moved out).
- ACCOUNT_QUERY / BATTLE_QUERY → `core/identifiers` (exact ID or trusted `web_base_url` URL) → client → account/battle template. A non-ID 账号 argument (≥2 chars) falls back to `GET /api/battles/users/search` (`main._account_search_outcome`): 0 hits ⇒ text, 1 hit ⇒ account page, several ⇒ `TargetType.ACCOUNT` candidates (search `limit=MAX_CANDIDATES`, upstream `hasMore` note appended). The smart route also searches accounts whenever the best board hit is weaker than the exact tiers (`> MatchLevel.PINYIN_EXACT`) and no options were given: an exact folded-nickname hit beats the fuzzy boards (1 exact ⇒ account page, several ⇒ account-only candidates), otherwise fuzzy account hits are appended to the board pick list; on a full board miss the quiet search runs before the character-name hint. Account-page rows with rank ≤3 get `tr.rank-N` medal styling (yellow/ink/muted)
- RANKING_QUERY / SMART_QUERY → `hot-bosses` cache → `core/matcher.RankingMatcher` → BOARD ⇒ `/api/bosses/{slug}/rankings` (ranking template; `--角色 X` filters rows after `core/characters.resolve_character_name` resolves X against the names in that ranking — exact → folded → pinyin → unique prefix/substring; `core/characters.pick_character_filter_scope` then picks MAIN (rows whose main C is X) and falls back to ROSTER (X anywhere in the four-man team) when the board has no main-C record — supports never carry, so a main-C-only filter would answer "nothing found" for exactly the characters people ask about; the page states the fallback and highlights the matched slot. NONE (X in no row at all) stays a short text reply. `--角色` takes every token up to the next option (`MAX_CHARACTER_FILTERS` = 4, joined with spaces in `RouteRequest.character_filter` so the candidate store needs no change); two or more names are resolved one by one and always mean ROSTER scope with *all* of them in the team (a team has one main C), rendered as 阵容含 A · B with every matched slot highlighted (`RankingPage.character_filters`), or a text reply when no team fields them all. Rows keep their global rank); DUNGEON / DUNGEON_SCOPE ⇒ filter hot-bosses cards (dungeon-top3 template); AMBIGUOUS ⇒ compact text list stored in `core/candidates.CandidateStore` (ends with `候选编号 XXXX · N 分钟内有效`); a reply that *quotes* that message with a number (bare, or `/zmdlog 2`) resolves it via `main._quoted_candidate_code`. Every entry is bound to the `unified_msg_origin` that received the list and `resolve(origin=)` refuses any other chat, and `extract_code` reads the *last* marker in the quoted text — the choice lines carry upstream nicknames, which could spell a marker themselves (`describe_choice` also collapses them to one line). `RankingMatcher.match` rejects queries longer than `MAX_QUERY_LENGTH` (64) outright: the fuzzy fallback is a sliding-window `SequenceMatcher` whose cost is linear in the query and it runs synchronously on the event loop, so an unbounded keyword was a one-message denial of service; replies that echo user text go through `main._shorten`
- CHARACTER_STATS (`/zmdlog 角色统计 [榜单或角色名] [--范围] [--潜能]`; bare `角色` is still accepted as an alias) → no keyword ⇒ `GET /api/bosses/character-statistics`; keyword ⇒ same matcher, but **board-only**: dungeon/scope hits are flattened with `RankingMatcher.expand_to_boards` into a candidate list (single board ⇒ rendered directly) → `GET /api/bosses/{slug}/character-statistics?range=&potential=` (never `metric`) → character-stats template. When the best board hit is weaker than the exact tiers (or misses), the query is resolved as a **character name** against the cached global catalog (`main._character_boss_outcome`) → `GET /api/characters/{key}/boss-statistics?range=&potential=` (own TTL cache, same config) → character-boss template (per-board rows sorted by median, `#rank / rankedCharacterCount` badge is the primary signal, shared box-plot CSS) (CSS box plots; axis spans whiskers, off-scale maxima pinned at 100%; crisis contract returns upstream 404 `character_statistics_not_available` → `危机合约不提供角色统计。`)
- ROSTER_QUERY (`/zmdlog 阵容 <关键词> [--top N]`) → same board-only pipeline → reuses the ranking cache → roster template (upstream `professionGroups` for the whole board + local top-N roster combos / main-character counts)
- `PendingCandidates.view` (`CandidateView.RANKING|CHARACTER_STATS|ROSTER`) plus the parsed options travel with the candidate list so a quoted pick renders the right page (`main._render_board` is the single place that renders one slug in any view)
- WATCH_LIST / WATCH_ADD / WATCH_REMOVE (`/zmdlog 关注 …` / `取关 …`, aliases 盯 / 不盯 / 取消关注) → text-only replies handled by `main._handle_watch_route` before `_dispatch`; adding resolves an id / URL / nickname exactly like 账号 does (several hits ⇒ `CandidateView.WATCH` pick list, resolved in `_reply_with_candidate`). WATCH_BOARD_ADD / WATCH_BOARD_REMOVE (`关注 榜单 <关键词>` / `取关 榜单 <序号或关键词>`, split off by `routing._board_watch_argument` — a nickname merely starting with 榜单 stays an account) live in the same handler: the keyword goes through the matcher and `expand_to_boards`, several boards ⇒ `CandidateView.WATCH_BOARD`. `core/watchlist.py` holds the immutable per-origin `WatchList` (`watchlist.json` v2: `{origin: {accounts, boards}}`, v1 bare account lists still load; accounts = public accountId + nickname snapshot + who added it + when, boards = slug + name snapshot + adder — no user identity); only the adder or an admin may remove an entry, and there is no cap by design. `board_label` lives here (re-exported by `core/watch`)
- TREND_QUERY (`/zmdlog 趋势 <昵称、accountId或主页链接> [--范围 7d|14d|30d|all]`, alias 名次趋势, default `DEFAULT_TREND_RANGE` = 30d, only `--范围` accepted) → `main._render_trend_outcome` reads `self.rank_history` and never upstream: an id / trusted URL is used directly; a nickname is first matched against the recorded display names (`_find_history_by_name`, exact folded then substring; several ⇒ `CandidateView.TREND` pick list) and only then goes through `_account_search_outcome(view=CandidateView.TREND)` (the same helper serves 账号; `view` decides which page a single hit draws); no trace ⇒ `_TREND_NO_DATA_MESSAGE`. `core/history.py` is pure: `record_rankings` appends a point per board only when the rank moved (a nickname change also counts as a change, a board missing from one response keeps its trace), `prune_points` keeps 90 days / 120 points per board but always the newest point (it *is* the current rank), `trend_points` pins the last pre-window rank to the window start so every line begins at the left edge, `window_start` maps 7d/14d/30d (all ⇒ None). `build_trend_page` (`resources/trend/`) draws one stepped polyline per board in a 100×44 viewBox with best rank on top, HTML-positioned dots at the change points and rows sorted by current rank; `--范围` reuses `RouteRequest.stats_range`
- ALIAS_LIST / ALIAS_ADD / ALIAS_REMOVE (`/zmdlog 别名 …`) → admin-only (`event.is_admin()`), edits the alias JSON in the data dir and swaps `self.aliases` in place

Supporting layers: `core/client.py` (httpx; 1 retry, 15s total budget, 4xx never retried, all failures → `ZmdLogsClientError` subclasses) → `core/models.py` (strict field-by-field validation into frozen dataclasses; `ModelValidationError` → `ZmdLogsProtocolError`) → `core/presentation.py` (view models, number/duration formatting, URL safety) → `core/render.py` (`TemplateRenderer` = Jinja with `StrictUndefined`; `LongImageRenderer` = Playwright capture with page-integrity validation, render semaphore, output pruning). `core/cache.py` `AsyncTTLCache` merges concurrent loads per key; only the hot-bosses cache allows stale-on-error.

`main.py` also registers a `@filter.regex` handler that auto-expands ZMDLogs battle links in group chats (off by default, per-group/battle cooldown). All three reply paths — the `zmdlog` command, the quoted candidate pick and auto-expand — run through one error ladder, `main._run_guarded` (API error → route-specific wording; client error → 暂时不可用; `RenderError` → AstrBot fallback render, else 图片生成失败; anything else → generic + `logger.exception`), so they cannot drift apart again; it also reports whether the failure was *transient*, which only the auto-expand cooldown reads: the claim is released only when nothing useful was sent and a repost could plausibly do better (client error, 5xx, capture failure without fallback) — a dead link (404) and an image delivered through the fallback renderer keep it. Account lookups reached from any route go through `main._render_account_outcome`, which answers a 404 in account terms regardless of which route kind caught it. Parse-layer `ValueError`s that are not `RouteParseError` get a short generic reply (defence in depth; `_parse_top` bounds its input before `int()`). Config ratios are clamped at load by `_ratio_or_default` (warn once, keep the default) so a typo like `65` cannot fail every keyword query. `_event_origin` returns `""` when the platform gives no origin — callers decide what that means (watch routes refuse, the candidate store keys on it, auto-expand only dedupes).

**Rank watch (顶屁股通知).** `main._rank_watch_loop` (started from `initialize`, which runs on every plugin load — `on_astrbot_loaded` fires once per process and would miss a market install or a config-triggered reload — and cancelled in `terminate`) polls every watched account once per cycle: `users/{id}/rankings` carries that account's `rank` on **every** board, so a whole watch list costs one request per account. Every request for one account stays inside the concurrency semaphore, and the board look-ups are capped at `MAX_DROPS_PER_NOTICE`. `core/watch.py` is pure. `find_rank_drops` reports only rank increases whose *previous* rank was inside `rank_watch_rank_threshold`, treats a board missing from the snapshot as a first sighting (never an event), and stays silent on improvements (a deliberate product decision). A baseline older than `max(3 × interval, 1h)` is discarded by `snapshot_is_usable` and re-seeded silently, so a restart after downtime does not replay everything that moved.

**Attribution is deliberately weak, and the wording must stay weak.** From one board read it is impossible to say who overtook the account: the row now at its *old* rank is usually a bystander pushed down by an insertion further up; a record posted in the window may be a player who was already ahead improving their own time; and `battleEndAt` is when the battle ended, not when it was uploaded, so a late upload can be the real cause while looking old. `find_new_record_above` therefore reports only what is provable — a record that is now ahead and postdates the previous check — takes its rank cutoff from the board response itself (not from the separately-cached account read), excludes the watched account, counts how many qualified, and returns `None` rather than guessing. The notice says 期间上方新增纪录, never 超过 TA 的是. Do not "improve" this into a causal claim without a real previous board state.

**Board watch (榜单新纪录).** `_run_board_watch_cycle` runs after the account cycle in the same loop and reads `hot-bosses` **directly from the client**, never through `hot_boss_cache` or the on-disk snapshot: an *older* top list diffed against the baseline would report runs that merely fell out of the top as new. One request per cycle covers every watched board. `core/watch.find_top_run_changes` reports the battle ids now in the top that were absent from `board-snapshot.json` (`BoardSnapshot` keeps nickname / main C / duration per run, so the notice can also name who fell out — that displacement *is* provable, unlike an account overtake); a first sighting and a shrunken list (a deleted record) are never events, and `board_snapshot_is_usable` applies the same staleness bound with an empty top list counting as a real state. 关注 榜单 seeds the baseline from the cached cards, 取关 榜单 drops it once nobody watches the board, notices merge per chat via `join_board_notices`.

Ranks persist in `rank-snapshot.json` (payload v2: `{accounts: {id: {checkedAt, ranks}}}`); 关注 seeds a baseline when none exists (so the first notice needs one cycle, not two) and never overwrites one another chat is waiting on, 取关 drops it once nobody watches the account, an account the cycle could not reach keeps its previous ranks, and a failed write warns once. The same cycle feeds the 趋势 trace: `_poll_watched_account` returns the full `PublicUserRankings` so the cycle can call `record_rankings`, `_seed_rank_snapshot` records the ranks held at 关注 time as the first points, `_forget_rank_snapshot` deletes the trace together with the baseline, and `rank-history.json` (v1: `{accounts: {id: {displayName, boards: {slug: {bossName, dungeonName, points: [[checkedAt, rank], …]}}}}}`) is only rewritten when a point was added or an account dropped. `core/timestamps.py` holds `utc_now_text` / `parse_timestamp` for all three modules (re-exported by `core/watchlist` and `core/watch` for existing imports). Notices are merged per chat per cycle (`join_rank_drop_notices`) because one new record demotes every watched account below it, and a burst of near-identical pushes is what gets a bot rate-limited. Delivery is `context.send_message(origin, MessageChain([Plain(text)]))` under a timeout, treating `False` as failure. 关注 列表 and 取关 keep working when `rank_watch_enabled` is off; only adding is refused. The cycle merges its results onto the live snapshot map and re-checks the watch list before sending, because 关注 / 取关 can run while it is awaiting — installing the map it started from would drop a baseline just seeded and notify a chat that has since unfollowed. The two text-only route families (别名 / 关注) are wrapped in their own error guard: they never reach `_dispatch`, so without it an unexpected error would surface as a traceback.

## Invariants to preserve

- **DPS only.** Never send `metric`, never show RDPS rankings; `parse_boss_ranking` rejects `metric != "dps"`.
- **Image-only output, with one carve-out.** Rank-watch notices and the 关注 / 取关 / 别名 replies are plain text: they are configuration actions and pushes, not query results. Any query/help result is one PNG; render failure returns a short error text, never a text fallback of the data. `_require_renderer()` raises `RenderError` if Playwright setup failed. When only the Chromium capture fails, `RenderError.html` carries the rendered page and `main._render_with_astrbot` retries through AstrBot's `html_render` (config `fallback_to_astrbot_renderer`, on by default) after neutralising Jinja delimiters.
- **Top-3 pages must not leak ranking-only fields** (slug, percentile, DPS, roster, links) — enforced by `test_top_three_template_does_not_leak_ranking_fields`.
- **User-facing errors are short and generic**; log only exception type / API code, never response bodies or stacks.
- **Strict for typed fields, lenient for untyped ones — and lenient for optional telemetry.** `models.py` validates every field the upstream Pydantic schema types; the two lists it leaves as bare dicts (`equips[].stats`, `equips[].enhanceLevels`) are read by `_parse_equip_stats` / `_parse_enhance_levels`, which keep well-formed entries and drop the rest, so one odd gear line can never fail a battle that used to render. `timelineEvents` and `characterStates` are typed upstream but read the same lenient way (`_parse_damage_points` / `_parse_character_state_buffs`, entry by entry, anything unreadable skipped): they only feed the DPS curve and the buff band, two sections the card must render without. Raw item ids are never printed as names (`is_raw_item_name` → 名称未收录); a raw buff key prints its effect instead of the key.
- **Help data (`core/help.py`) must be updated whenever a user-facing command changes**; `test_routing_help` asserts the exact command list. Every `HelpCommand` carries an `answers` line — the question that command answers, ending in `？` (asserted by the same test) — because 阵容 / 角色统计 / `--角色` are indistinguishable from their syntax alone; sections are grouped by what the reader wants to know and each carries a one-line `summary`. Version comes from `metadata.yaml`, don't hardcode.
- Rendered pages must contain `#zmd-page > .main-panel` and the local background data-URL (`resources/common/scene-background.svg`, inlined as `data:image/svg+xml`), or `_validate_page` fails the render. Templates extend `resources/common/base.html`; page-specific CSS is `{% include %}`d into `extra_styles`. Decorative elements that overflow must live inside `.scene-deco` (overflow hidden) or `#zmd-page` scrollWidth exceeds 1280 and validation fails.
- **Visual language is Endfield-style** (light paper `#f1f1ee`, ink `#1c1c1c`, accent yellow `#f8d34d`, cut corners via `clip-path`, skewed badges, Barlow for Latin/digits, MiSans for CJK). Fonts are subset woff2 files (CJK = full GB2312, 6763 chars) in `resources/common/fonts/` embedded as data URLs by `core/render._load_font_face_css`; regenerate with `tools/build_fonts.py <dir-with-source-ttfs>` (needs fonttools+brotli, see `resources/common/ASSETS.md`). No AGPL assets remain.
- Avatar URLs from upstream are site-relative; every page builder takes `web_base_url` and resolves via `_safe_asset_url` (unsafe schemes → `None`). `core/identifiers` compares origins with default ports normalised (`https://host:443` ≡ `https://host`) and treats a malformed port (`:abc`, `:99999`) — in the link *or* in the configured `web_base_url` — as "not a trusted link", never as a raised `ValueError`.
- `hot-bosses` is the sole source of the board/dungeon index — no hardcoded board catalog; a JSON snapshot of the last good payload is kept in the data dir (`hot-bosses.json`) and used when upstream is unreachable. Matching derives aliases automatically (`derived_board_aliases`: strip `·苦难/·残酷` suffix and `{dungeon}·` prefix; `derived_dungeon_aliases`: split `影拓丰碑4期 · 山中见犼` into parts + `丰碑4/影拓4`) and pinyin keys (`pypinyin`, full + initials, `MatchLevel.PINYIN_EXACT`; a CJK query is also compared by its own full pinyin so homophone typos like 躁雷→噪雷 hit as PINYIN_EXACT 0.98 / PREFIX_SUFFIX 0.85). A single below-threshold similarity hit renders directly; only ≥2 weak hits become a pick list. An exact hit on several dungeons of one phase becomes a DUNGEON_SCOPE instead of AMBIGUOUS; an exact hit on a one-board dungeon is promoted to that board. Hand-written aliases live in `aliases.json` (`boards` keyed by `bossSlug`, `dungeons` keyed by full `dungeonName`); the bundled file only seeds `data/plugin_data/astrbot_plugin_zmdlog/aliases.json`, which is the editable copy.
- Only image requests to `api_base_url` / `web_base_url` origins are allowed during capture; everything else is aborted. The Playwright route handler only ever sees the first hop of a redirect chain, so allowed image requests are fetched *inside* the handler (`route.fetch(max_redirects=0)`) and any 3xx is aborted; 200-responses are kept in `render.AssetCache` (in-memory, 6h TTL, 32MB total / 2MB per item, insertion-order eviction) because every capture runs in a fresh incognito context and would otherwise re-download the whole static avatar catalog per render — otherwise a redirect served by an allowed origin would pull the image from anywhere. This has no unit test (needs Chromium); verify with a two-local-origins script when touching `_route_asset_request`.

## Config

`_conf_schema.json` is the AstrBot config schema; defaults are duplicated in `main.py.__init__` `.get(...)` calls — keep both in sync. `README.md` documents commands/config for end users and must be updated alongside. Rendered PNGs go to `StarTools.get_data_dir("astrbot_plugin_zmdlog")/render` (falls back to system temp when StarTools is unavailable); `@filter.on_astrbot_loaded` warms up Chromium. `_HIGH_DPI_PAGE_KINDS` in `render.py` (help, ranking, account, battle, character-stats, character-boss, roster, loadout, skills, trend, timeline) are captured at `device_scale_factor=2` (PNG 2560px wide); the long top-3 pages stay 1x. `metadata.yaml` carries `short_desc`; `logo.png` (256×256) is the market icon.

## Upstream facts (verified against endfield-suite-open `apps/api/app/services/public_data.py`)

- `characterAvatarUrl` / `avatarUrl` in hot-bosses, rankings and battles are usually **site-relative paths** (`/images/...`), occasionally absolute CDN URLs — resolve them against `web_base_url` before rendering.
- In battle detail every `roster[].accountDisplayName` is the uploader nickname, so `roster[0]` is a valid uploader name source; `GET /api/battles/{id}/share-summary` also returns `uploaderNickname` directly.
- Battle detail `roster[]` carries the loadout recorded at upload: `slot` (1-based), `characterElement` (`physical|fire|cryst|natural|pulse` = 物理/灼热/寒冷/自然/电磁), `characterLevel`, `characterPotential`, `weapon{weaponName, weaponLevel (often null/0), weaponRefine, iconUrl, skills[{skillKey, level, potentialLevel}]}` where `sk_wpn_*` is the weapon's own skill and `wpn_attr_*` / `wpn_sp_attr_*` are affixes, `equips[]` (4 pieces: 护手 / 护甲 / 配件 ×2; `pieceName` falls back to the raw `item_equip_…` id with `suitName` null when the catalog has no name; `enhanceLevels[{index, level}]`; `stats[{slot: main|sub1..3, name, value, level}]` with ratio stats as fractions, e.g. 0.1495, and occasionally untranslated names `Main` / `副能力`), and `skills[{skillKey, level}]` (`_attack1..5`, `_normal_skill`, `_combo_skill`, `_ultimate_skill`, talents at level 1). Older uploads (crisis-contract era, parser < v34) have empty weapon skills / stats / enhance lists. `roleSkillStats[]` (`characterName, skillKey, skillName, castCount, totalDamage, avgDamage, maxDamage`) is per damage source: the normal attack chain is one row per segment, `skillName` may be a raw key or English placeholder (`burning status`, `poise can be breaking attacked`), and `buff_common_*` rows are engine-side damage (element reactions, statuses). `timelineEvents[]` (`tsMsFromStart`, `laneType: skill|buff`, `sourceCharacterName`, `value`, `durationMs`, `effects[{zone, element, rate}]`, `poiseDamage{value, current_value}`, …) is the per-hit log: 171 events / 0.2 MB for a 22 s run, 1868 / 1.9 MB for a six-minute one, parsed in ~12 ms. Its damage values sum **exactly** to `battle.totalDamage`, and per `sourceCharacterName` to each `participants[].totalDamage`, which is what makes the DPS curve reconcile with the table above it. `characterStates[]` (`characterName`, `loadout`, `initialBaseline`, `buffsReceived|buffsGiven|debuffsApplied[{eventKey, eventName, sourceCharacterName, targetCharacterName, startTsMsFromStart, durationMs, effects}]`) is the same buff data pre-grouped per character, and is the source the buff band uses. `poiseDamage` (失衡) is present but deliberately **not** drawn: speed runs sample it a handful of times and never break it, there is no cap field (upstream's 上限 is the max observed), so the lane would be a flat line on exactly the fights people look at.
- Board slugs come from static `BOSS_SEEDS`; the crisis-contract board is `indie_group_ccdg` (`bossName` 破潮之像, `dungeonName` 危机合约). Unknown slug → 404 `boss_not_found`.
- `GET /api/characters/{character_key}/boss-statistics` (same `range`/`potential`/`metric` params) returns one character's row for **every** statistics board (zero-sample rows included; crisis contract and inactive season towers excluded); each row equals the character's row in the matching per-board response, plus `rankedCharacterCount`. Unknown key → 404 `character_not_found`. Admin operator is unified as `chr_9000_endmin`.
- `GET /api/bosses[/{slug}]/character-statistics` (`range=7d|14d|30d|all`, `potential=0|1-5|all`, `metric` defaults to dps) returns every six-star character (`SIX_STAR_STATISTICS_CATALOG`), zero-sample rows included; `rank` is null when `normalSampleCount < minimumSampleCount` (5); whiskers are min/max of IQR-filtered normal samples, `maximum` includes outliers. Crisis contract → 404 `character_statistics_not_available`. `professionGroups[].entries[].usagePercent` is the share within that profession slot over **all** rows.
- `GET /api/v1/battles/{battle_id}/export` (public, no token, per-IP 60 requests/min → 429 `rate_limited`, `Cache-Control: max-age=60` + weak ETag, CORS `*`; the read-only contract upstream keeps for external axis tools) returns `{schemaVersion: 1, battleId, parserVersion, rulesVersion, dungeon{dungeonSlug, dungeonName, bossKey, bossName}, durationMs, battleStartAt, battleEndAt, roster[…], casts[…]}`. `roster` is the detail roster minus profession / avatar / element / accountDisplayName; `casts[]` = `{tsMsFromStart, endMsFromStart|null, characterKey, skillKey, skillName, skillSource: "unknown"|"Summon", recoversEnergy}` and includes normal-attack segments and summoned entities' casts; `tsMsFromStart` can be negative (before the timer), `endMsFromStart` null or past `durationMs`, 10–110 casts per speed run. 404 for a non-public battle, 422 `battle_export_unsupported` for uploads older than parser v33 (no casts; the crisis-contract era). The web's per-hit `timelineEvents` in the detail response (1.6 MB for a six-minute fight) is *not* used for the timeline.
- `GET /api/battles/users/search?query=&limit=` (public, no auth): NFKC-normalized case-insensitive substring match over public nicknames; `query` must be 2–64 chars after strip (else 422), `limit` 1–20 (default 10); returns `{query, hasMore, accounts[{accountId, accountDisplayName}]}`, only accounts with valid public ranking records. Server caches ≤60s, HTTP `max-age=30`. Full contract in local `PUBLIC_ACCOUNT_SEARCH_API.md`-style doc (Downloads).
