# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

AstrBot plugin (`ZmdLogBot`) that queries public ZMDLogs data (Endfield DPS leaderboards, account best records, battle reports) and replies with a single 1280px-wide PNG rendered by Jinja2 + Playwright. Entry point is `main.py` (`ZmdLogBotPlugin(Star)`, ~630 lines of AstrBot glue: the handlers, the error ladder, event field access, the notice sender, the lifecycle); all logic lives in `core/`, which never imports AstrBot. The plugin wires five services in `__init__`: `core/settings.PluginSettings` (config read once, validated), `core/datasource.ZmdLogsDataSource` (every upstream read and its cache), `core/alias_admin.AliasAdmin` (the 别名 commands and the alias file), `core/rank_watch.RankWatcher` (关注 / 取关, both polling cycles, four JSON files) and `core/queries.QueryService` (everything between a parsed route and the image or text it produces). Modules that need to log take a `core/logs.LogSink` (AstrBot's plugin logger is not a `logging.Logger`); shared reply wording lives in `core/messages.py`. Python 3.10+, deps in `requirements.txt` (httpx, jinja2, playwright, pypinyin). Chromium must be installed separately (`python -m playwright install chromium`).

## Commands

```bash
.venv/Scripts/python.exe -m unittest discover -s tests -v          # full suite (~300 tests, ~12s)
.venv/Scripts/python.exe -m ruff check main.py core tests tools    # lint (ruff.toml: E/F/I/W, py310)
.venv/Scripts/python.exe -m unittest tests.test_matcher -v         # one module
.venv/Scripts/python.exe -m unittest tests.test_matcher.MatcherTests.test_slug_and_board_aliases_match_one_board
```

Tests import `core.*` directly (run from repo root). Playwright is *not* exercised by tests — render tests only cover template output and validation logic. Lint with ruff (`ruff.toml`); `ruff format` is not enforced on the existing files. Runtime is inside AstrBot (`data/plugins/astrbot_plugin_zmdlog`); keep `core/` free of AstrBot imports so it stays unit-testable. AstrBot itself is installed in `.venv`, so `main.py` *can* be driven: `tests/test_main_handlers.py` imports it as the package `astrbot_plugin_zmdlog.main` (repo parent on `sys.path`), sets `main.StarTools = None` so nothing touches the real data dir, and feeds it fake events/clients/renderers — it is skipped wherever AstrBot is absent. Importing `tests/` replaces the httpx transports with one that raises `NetworkAccessInTests` naming the URL: the suite must run offline, or it measures upstream and goes red during an outage. The handler `setUp` answers the export, the nickname search and the six-star catalog as an outage unless a test stubs them. Two traps when writing such tests: exceptions must come from `astrbot_plugin_zmdlog.core.*` (the package's class identities, which `main.py` catches), not from `core.*`; and merely importing `astrbot.api` creates a `./data` directory in the CWD (gitignored).

## Architecture (request flow)

`main.py` → `core/routing.parse_zmdlog_payload` (subcommand + trailing `--top` / `--角色` / `--范围` / `--潜能` options, parsed by `_extract_options`; each route rejects options it does not accept) → `QueryService.dispatch` (`core/queries.py`; `_dispatch_direct` for routes that name their target, `_dispatch_keyword` for the board matcher, `_answer_board_miss` for the fallbacks when no board matched):
- HELP → `core/help.build_help_page` (local only, no API)
- BATTLE_QUERY with a non-reference argument falls through to the board-only pipeline as `CandidateView.BATTLE` (routing pre-splits a trailing rank token — `战报 罗丹 3` / `第3` / `#3`, default 1, stored as `RouteRequest.battle_rank`); `QueryService._render_board` picks the ranking row with that rank and renders its battle summary. LOADOUT_QUERY (`配装`, alias `装备`) and SKILL_QUERY (`技能`, alias `技能统计`) take the identical argument shape (`routing._BATTLE_STYLE_COMMANDS`) and share the whole lookup (`queries.BATTLE_STYLE_ROUTES` / `_BATTLE_VIEWS`, `CandidateView.LOADOUT|SKILLS`); only `QueryService._render_battle_view` differs, drawing the loadout or skills page and answering in text (`messages.NO_LOADOUT` / `messages.NO_SKILL_STATS`) when an older upload carries no roster or no `roleSkillStats`. The battle card itself ends with a 阵容与配装 section (per-slot Lv / 潜能 / 精炼 / suit lines + top-3 damage sources). `core/loadout.py` is the pure layer: skill display names and categories mirror upstream `apps/web/lib/format/skill-display.ts` (plus 机制 / 套装 / 武器 buckets for `buff_*` keys). Upstream names a damage row from the game's text table when it can and otherwise joins the key's segments with ` / `, translating some tokens (`普攻 / skill / 派生 / hit` for `…_normal_skill_projhit_hit`, which is wrong: `normal_skill` is one phrase, the 战技). `skill_display_name` therefore has three layers: the override dictionaries (`_SKILL_KEY_OVERRIDES` / `_SKILL_NAME_OVERRIDES`, hand-written, the site's own entries copied), then **`_humanise_key`** for any name that is still upstream's token join of a `chr_…` / `buff_chr_…` / `buff_common_…` key (`_named_from_key`: same word count as the key's segments and every Chinese word one of the token labels — a name with text of its own, `塞什卡的秘传 / phantom` or `召唤 / pet`, is never overwritten), which reads the family (`_SKILL_FAMILIES`: 战技 / 终结技 / 连携技 / 重击 / 下落攻击 / 闪避攻击), parser_core's reaction names (`_reaction_name`: 自然爆发, 燃烧 …, tolerating a trailing character token) and the token table (`_KEY_TOKEN_LABELS`, parser_core's `_humanize_skill_suffix_text` plus the tokens the boards actually show), then `_translate_name_segments` for everything else. A lone `common_<element>_triggered` is that element being applied (自然附着), and `weakness` is the 脆弱 debuff — both confirmed in play by the user on 2026-09-05, as were the dictionary entries for 青霆剑 (庄方宜), 燃烧, 衔火血翼 (卡缪) and 诀's three numbered 连携 follow-ups, which share the name 连携技 · 战术分身 and therefore fold into one row on purpose. `skill_category` buckets by the family before the ` · `, so `连携技 · 持续伤害` is COMBO. Across the top runs of every board this took rows still carrying English from 748 to 18 (three names, all needing game knowledge: see the override dictionaries). The timeline uses the same function for cast labels; the only cast it changed is `…_combo_skillfloating` → 连携技 · 浮空, `group_skill_damage` folds the A1–A5 normal-attack chain and same-name rows (three "终结技" sub-hits) into one row, the suit of a piece comes from the **game data catalog** (`GET /api/game-data/equip`, cached for 30 days by `ZmdLogsDataSource.get_equip_suits`, passed into the page builders as `suits`): `suit_catalog_id` turns `item_equip_t4_suit_spellburst_hand_01` into `suit_spellburst` and the catalog names it 险关. Upstream's per-battle `suitName` is only the fallback, because it is not a property of the item (see Upstream facts) and has been seen naming a different suit outright. A `_parts_` piece belongs to no suit, so `suit_catalog_id` returns `None` and upstream's label (独立装备) stands. Over 2835 pieces in the top runs of every board this took the share carrying a suit name from 81% to 98% and corrected 149 wrong ones, `skill_level_summary` picks 普攻/战技/连携/终结 levels by key suffix. Templates: `resources/loadout/`, `resources/skills/`, shared `resources/common/loadout.css`; weapon / equip icons are site-relative like avatars, and when upstream omits `iconUrl` (its catalog does not know the piece yet, while the file exists) `presentation/common._derived_asset_url` builds the conventional `/images/equip/iconbig/{itemId}.png` / `/images/weapon/icon/{weaponTemplate}.png` path, which the template's `onerror` drops if wrong. TIMELINE_QUERY (`技能轴`, aliases `排轴` / `时间轴`) takes the same argument shape but reads the public export (`client.get_battle_export`, own `battle_export_cache`) instead of the battle detail: `_render_battle_view` takes the battle *id* and fetches whichever payload the view needs, and answers a 422 `battle_export_unsupported` (upload too old to carry casts) or a 429 in text (`queries._export_refusal` → `messages.NO_TIMELINE` / `messages.TIMELINE_RATE_LIMITED`) right there, so every route that reaches a battle gets the same wording. `core/timeline.py` is pure: `classify_cast` applies name rules, then *end-anchored* key rules ported from upstream `apps/web/lib/endaxis-project.ts` — a mechanism entity such as `…_combo_skill_water_gene` must not be drawn as the player's 连携技 (upstream's own "汤汤 连携×3" incident) — and hides movement noise (dodge / dash / sprint / idle / born / die / hitstop / switch, `plunging_attack_end`); `build_timeline` drops pre-timer casts, clips casts past `durationMs` and **folds bursts** per lane (`_fold`: consecutive normal-attack segments within `MERGE_GAP_MS` become one 普攻 run, the same move fired again within the gap becomes one event with a count; summon-sourced casts, `skillSource == "Summon"`, form a second stream). **The chart is a vertical rail** (`resources/common/timeline-rail.html` macro + `resources/common/timeline.css`, shared by the battle card's 施法节奏 section and the 技能轴 page) built on one rule from the user's design memo: 线管连续、长度管时长、宽度与颜色管招式层级、节点管瞬时. Time runs down; every character has a 2 px idle rail line at `_RAIL_X_PX`; each folded event with a known end is a bar growing rightwards from the line, as tall as it lasts (min 5 px) and as wide as its kind matters (`_RAIL_BAR_PX`: 普攻 8, 其他 12, 战技/连携/重击 16, 终结技 20, the last with a diamond landmark); an instant is a 7 px dot (diamond for a 终结技); own moves that overlap step right into further columns (`_rail_columns`, `_RAIL_COLUMN_STEP_PX`) and the lane's labels move with them (`RailLaneView.label_left`); summons keep to an 8 px hatched strip left of the line; a heavy that recovers energy gets a yellow dot. Labels (`time · name ×n`) start at `_RAIL_LABEL_LEFT_PX`, slide down when neighbours are closer than one 15 px line, are dropped past a per-category slack (an ultimate never), and a narrow bar gets a hairline leader to its label while the label is still level with it. `build_timeline_view` picks the scale per host: the card targets ≈ 560 px (6–24 px/s), the page ≈ 1600 px (10–40 px/s); the tick step is the first of 1/2/5/10/30/60 s that is ≥ 34 px apart. Four layouts came before this one and must not come back: horizontal 20-second strips (the fixed 1280 px width could not fit a name into a half-second cast), full-width vertical blocks ("一整块砸下来"), a hairline rail with dots (too thin to read without zooming), and a uniform 44 px track (the light-grey normal-attack runs read as columns of filler); the user's memo of 2026-09-03 settled the graded widths. Portraits use the observed `/images/character/charremoteicon/icon_{key}.png` convention because the export has no avatar URLs; the `<img onerror>` drops a wrong guess. The battle card fetches the export best-effort (`QueryService._battle_export_for_card`: 422 / 429 become a one-line note, anything else silently omits the section), so 战报 and the auto-expand path never fail because the export did; detail and export go out **together** (`_battle_with_export`, and the same `gather` on the 技能轴 page) because each read has its own 15-second client budget and awaiting them in sequence put the optional section in front of the payload
- COMPARE_QUERY (`对比`, alias `比较`) → `routing._parse_compare`: two reference-shaped tokens (link / `btl_*`) become `query` + `compare_target` and skip the board lookup; otherwise up to two ranks are read off the tail (`battle_rank`, `compare_rank`; none ⇒ 1 vs 2, one ⇒ 1 vs it, equal ⇒ error) and the keyword goes through the board-only pipeline as `CandidateView.COMPARE` (`PendingCandidates.compare_rank` travels with the pick list; `_render_board` resolves both ranks and names the first missing one). `QueryService._render_compare` fetches both details concurrently (same id ⇒ text; different `boss_name` ⇒ text, because every boss has its own rotation and the user ruled cross-boss comparison meaningless) and `presentation/compare.build_compare_page` builds the two `BattlePage`s the card would draw and composes them: facts with the better side marked (time lower, DPS / damage higher; deltas as seconds / percent of the lower side), the roster union in A's order with absent sides marked, both *team* DPS lines on one shared axis (`_compare_curve`: the shorter fight's line simply stops, dashed end markers), and per character the gear lines (`_gear_lines`: 等级·潜能, 武器·精炼, four pieces, skill levels) with differing lines flagged. A gear line carries **two** values (`_GearLine`): the text to print, and the `item_id` that decides whether the line differs — comparing the printed suit label called identical gear different on 11 of the 37 characters who wore the same pieces on both sides. The two 配件 rows are paired by item id (`_pair_accessories`), because the same pair sits in slot 2/3 for one player and 3/2 for another; **A keeps the order its own 配装 page shows and B is matched to it**, since sorting both sides aligned them but left neither matching the page a reader cross-checks against plus each side's top-3 damage sources. Template `resources/compare/`; A is yellow and B blue throughout. The 技能轴 page also fetches the detail best-effort (`QueryService._battle_detail_if_available`) only to add the BUFF 覆盖 band above its rail.
- ALL_RANKINGS → `ZmdLogsDataSource.list_hot_bosses` (the `hot-bosses` cache) → all-top3 template
- The battle card carries two more charts built from the same response by `core/telemetry.py` (pure) and `presentation/charts.build_dps_curve_view` / `build_buff_band_view`, both `None` when the upload has no telemetry: **DPS 曲线** buckets damage per second and divides the running total by elapsed time (the board's own reading, so each line ends at that character's DPS in the table above; the line colour is the participant's `share-seg--N` index, and the team line is included in the axis peak or it would clip flat), and **BUFF 覆盖**, its own section directly under the curve: one row per buff keyed by (name, effect, source) so upstream's caster / owner / weapon-tag variants of one buff merge into a single uptime row, applications within `TEAM_MERGE_GAP_MS` (80 ms) fold into one span, overlapping refreshes merge, only damage zones (`atk` / `dmg_inc` / `amp` / `combo`) qualify, and rows past `MAX_BUFF_ROWS` (12) are counted in a note. Both live in `resources/common/battle-charts.{html,css}` and share one three-column skeleton (`.hchart-row`: 232 px side | track | 40 px gutter) and one tick set (`_horizontal_ticks`), so their time axes line up and a buff bar can be read against the curve above it; the curve's legend therefore sits in the left column, not under the plot. The section order is DPS 曲线 → BUFF 覆盖 → 施法节奏 so the one switch from left-to-right to top-to-bottom time coincides with a heading (the band was first placed inside the 施法节奏 section and the user asked for it to be moved out).
- ACCOUNT_QUERY / BATTLE_QUERY → `core/identifiers` (exact ID or trusted `web_base_url` URL) → client → account/battle template. A non-ID 账号 argument falls back to `GET /api/battles/users/search` (`QueryService._account_search_outcome`; `client.searchable_nickname` decides whether the text is worth a request with the same NFKC-normalised 2–64 character measure the request applies): 0 hits ⇒ text, 1 hit ⇒ account page, several ⇒ `TargetType.ACCOUNT` candidates (search `limit=MAX_CANDIDATES`, upstream `hasMore` note appended). The smart route also searches accounts whenever the best board hit is weaker than the exact tiers (`> MatchLevel.PINYIN_EXACT`) and no options were given: an exact folded-nickname hit beats the fuzzy boards (1 exact ⇒ account page, several ⇒ account-only candidates), otherwise fuzzy account hits are appended to the board pick list; on a full board miss the quiet search runs before the character-name hint. Account-page rows with rank ≤3 get `tr.rank-N` medal styling (yellow/ink/muted)
- RANKING_QUERY / SMART_QUERY → `hot-bosses` cache → `core/matcher.RankingMatcher` (built once per (cards, aliases) pair by `matcher.MatcherCache`, compared by identity — the pinyin index costs tens of milliseconds, a match a few) → BOARD ⇒ `/api/bosses/{slug}/rankings` (ranking template; `--角色 X` filters rows after `core/characters.resolve_character_name` resolves X against the names in that ranking — exact → folded → pinyin → unique prefix/substring; `core/characters.pick_character_filter_scope` then picks MAIN (rows whose main C is X) and falls back to ROSTER (X anywhere in the four-man team) when the board has no main-C record — supports never carry, so a main-C-only filter would answer "nothing found" for exactly the characters people ask about; the page states the fallback and highlights the matched slot. NONE (X in no row at all) stays a short text reply. `--角色` takes every token up to the next option (`MAX_CHARACTER_FILTERS` = 4, joined with spaces in `RouteRequest.character_filter` so the candidate store needs no change); two or more names are resolved one by one and always mean ROSTER scope with *all* of them in the team (a team has one main C), rendered as 阵容含 A · B with every matched slot highlighted (`RankingPage.character_filters`), or a text reply when no team fields them all. Rows keep their global rank); DUNGEON / DUNGEON_SCOPE ⇒ filter hot-bosses cards (dungeon-top3 template); AMBIGUOUS ⇒ compact text list stored in `core/candidates.CandidateStore` (ends with `候选编号 XXXX · N 分钟内有效`); a reply that *quotes* that message with a number (bare, or `/zmdlog 2`) resolves it via `main._quoted_candidate_code`. Every entry is bound to the `unified_msg_origin` that received the list and `resolve(origin=)` refuses any other chat, and `extract_code` reads the *last* marker in the quoted text — the choice lines carry upstream nicknames, which could spell a marker themselves (`describe_choice` also collapses them to one line). `RankingMatcher.match` rejects queries longer than `MAX_QUERY_LENGTH` (64) outright: the fuzzy fallback is a sliding-window `SequenceMatcher` whose cost is linear in the query and it runs synchronously on the event loop, so an unbounded keyword was a one-message denial of service, and `_partial_similarity` reuses one `SequenceMatcher` across windows with a `quick_ratio` bound (same maximum, a fifth of the cost); replies that echo user text go through `messages.shorten`
- CHARACTER_STATS (`/zmdlog 角色统计 [榜单或角色名] [--范围] [--潜能]`; bare `角色` is still accepted as an alias) → no keyword ⇒ `GET /api/bosses/character-statistics`; keyword ⇒ same matcher, but **board-only**: dungeon/scope hits are flattened with `RankingMatcher.expand_to_boards` into a candidate list (single board ⇒ rendered directly) → `GET /api/bosses/{slug}/character-statistics?range=&potential=` (never `metric`) → character-stats template. When the best board hit is weaker than the exact tiers (or misses), the query is resolved as a **character name** against the character catalog (`ZmdLogsDataSource.get_character_catalog`: names and keys taken from the global statistics response, which upstream takes ~5 s to compute, kept 30 days because only a new character changes them, and re-read at most once per 10 minutes when a name misses — the 角色统计 route and the tool ask for that refresh, the hint text does not; `QueryService._character_boss_outcome`, sharing `_resolve_catalog_character` with the hint text) → `GET /api/characters/{key}/boss-statistics?range=&potential=` (own TTL cache, same config) → character-boss template (per-board rows sorted by median, `#rank / rankedCharacterCount` badge is the primary signal, shared box-plot CSS) (CSS box plots; axis spans whiskers, off-scale maxima pinned at 100%; crisis contract returns upstream 404 `character_statistics_not_available` → `危机合约不提供角色统计。`)
- CHARACTER_STANDINGS (`/zmdlog 角色排名 <角色名>`, alias 角色榜, no options) → `QueryService._render_character_standings`: `ranking_index.ensure_filled()` (shares a fill in progress; with the loop disabled this is the on-demand 13 s read), the name resolved with `resolve_character_name` against every roster the index holds (`standings.roster_character_names`, so four-stars count, unlike the six-star catalog), `core/standings.character_standings` (pure: per board the best-ranked row whose roster fields X, its rank among *all* records on that board, appearances and main-C count; boards without X folded into `absent`), drawn by `presentation/standings.build_character_standings_page` (`resources/character-standings/`, reusing the ranking row CSS) with `index.oldest_age_seconds()` as the 数据截至 label, because the page is drawn from memory. These are a *team's* results and the text says so; the text also states the counts a model gets asked for (第一名 / 前三 / 前十, first places as main C) and names every first-place board, because the detailed rows stop at the row limit. **Without a name** (`角色排名` bare, or the tool's `character` left empty) the same records are counted per character instead of listed per board: `standings.character_tallies` (a board's #1 record gives each of its four members a 冠军 — the user's definition, 2026-09-06, headline and sort — `first_places_as_main` counts the ones where the character was that record's main C as a side note, podiums / top tens count boards by the character's best rank there) drawn by `presentation/champions.build_character_champions_page` (`resources/character-champions/`; characters with a podium as rows, the rest folded into chips), followed by the most common first-place compositions (`standings.first_place_teams`) and who fills each profession slot across every record (`standings.profession_usage`, counted from rosters, share = records fielding the character over all records). `--范围 7d|14d|30d` on the bare command (tool `range`) narrows every board to the records of the window first (`standings.window_rows`; positions are re-counted from one inside the window, so the window's first place is its fastest record whatever its overall rank); `history.window_label` names it on the page and in the text. The character tool draws the standings page when no board is given, resolving against rosters first and falling back to the six-star catalog (distribution page) for a name with no record; the DPS lines are appended only when the catalog knows the name.
- **Elements** come from `GET /api/game-data/character` (`charTypeName`: 物理 / 灼热 / 寒冷 / 自然 / 电磁, plus `weaponTypeName`; `ZmdLogsDataSource.get_character_types`, kept 30 days like the suits) — ranking rows carry no element, and battle rosters carry it per battle only. `core/elements.py` normalises what people type (火 → 灼热, 雷 → 电磁, `--element`). `--属性 X` filters a board page's rows by the *main C's* element (`RankingPage.element_filter`, composes with `--角色`) and a bare `角色排名` by the characters' element (the champions board restricted to them, which is how 物理队有什么冠军 is answered; with a name the option is rejected); the tools take `element` on the board and character tools. Every roster avatar gets a ring in the element's colour (`RosterEntryView.element_key`, `.avatar.el-*` in `base.css`) with a legend line under the table; the user asked for the filter and the rings only — no element chip, no element text, no element statistics page (2026-09-06).
- ROSTER_QUERY (`/zmdlog 阵容 <关键词> [--top N]`) → same board-only pipeline → reuses the ranking cache → roster template (upstream `professionGroups` for the whole board + local top-N roster combos / main-character counts)
- `PendingCandidates.view` (`CandidateView.RANKING|CHARACTER_STATS|ROSTER`) plus the parsed options travel with the candidate list so a quoted pick renders the right page (`QueryService._render_board` is the single place that renders one slug in any view; `main._reply_with_candidate` resolves the code and calls `QueryService.render_pick`)
- WATCH_LIST / WATCH_ADD / WATCH_REMOVE (`/zmdlog 关注 …` / `取关 …`, aliases 盯 / 不盯 / 取消关注) → text-only replies handled by `RankWatcher.handle_route` (`core/rank_watch.py`; `main.py` passes the origin, the sender key and the admin flag) before any query dispatch; adding resolves an id / URL / nickname exactly like 账号 does (several hits ⇒ `CandidateView.WATCH` pick list, resolved in `main._reply_with_candidate` via `RankWatcher.remember_account`). WATCH_BOARD_ADD / WATCH_BOARD_REMOVE (`关注 榜单 <关键词>` / `取关 榜单 <序号或关键词>`, split off by `routing._board_watch_argument` — a nickname merely starting with 榜单 stays an account) live in the same handler: the keyword goes through the matcher and `expand_to_boards`, several boards ⇒ `CandidateView.WATCH_BOARD`. The four files are `persistence.JsonStore`s on the watcher (`watchlist_store`, `rank_snapshot_store`, `board_snapshot_store`, `history_store`), each warning once per failure streak. `core/watchlist.py` holds the immutable per-origin `WatchList` (`watchlist.json` v2: `{origin: {accounts, boards}}`, v1 bare account lists still load; accounts = public accountId + nickname snapshot + who added it + when, boards = slug + name snapshot + adder — no user identity); only the adder or an admin may remove an entry, and there is no cap by design. `board_label` lives here (re-exported by `core/watch`)
- TREND_QUERY (`/zmdlog 趋势 <昵称、accountId或主页链接> [--范围 7d|14d|30d|all]`, alias 名次趋势, default `DEFAULT_TREND_RANGE` = 30d, only `--范围` accepted) → `QueryService._dispatch_trend` / `_render_trend` read the watcher's trace (`RankWatcher.history_for` / `history_by_name` / `last_checked`) and never upstream: an id / trusted URL is used directly; a nickname is first matched against the recorded display names (`RankWatcher.history_by_name`, exact folded then substring; several ⇒ `CandidateView.TREND` pick list) and only then goes through `_account_search_outcome(view=CandidateView.TREND)` (the same helper serves 账号; `view` decides which page a single hit draws); no trace ⇒ `_TREND_NO_DATA_MESSAGE`. `core/history.py` is pure: `record_rankings` appends a point per board only when the rank moved (a nickname change also counts as a change, a board missing from one response keeps its trace), `prune_points` keeps 90 days / 120 points per board but always the newest point (it *is* the current rank), `trend_points` pins the last pre-window rank to the window start so every line begins at the left edge, `window_start` maps 7d/14d/30d (all ⇒ None). `build_trend_page` (`resources/trend/`) draws one stepped polyline per board in a 100×44 viewBox with best rank on top, HTML-positioned dots at the change points and rows sorted by current rank; `--范围` reuses `RouteRequest.stats_range`
- ALIAS_LIST / ALIAS_ADD / ALIAS_REMOVE (`/zmdlog 别名 …`) → `core/alias_admin.AliasAdmin.handle`, admin-only (`event.is_admin()`), edits the alias JSON in the data dir and installs a new `AliasConfig` (the matcher cache compares aliases by identity, so the next query rebuilds its index)

Supporting layers: `core/client.py` (httpx; 1 retry, 15s total budget, 4xx never retried, all failures → `ZmdLogsClientError` subclasses) → `core/models.py` (strict field-by-field validation into frozen dataclasses; `ModelValidationError` → `ZmdLogsProtocolError`) → `core/presentation.py` (view models, number/duration formatting, URL safety) → `core/render.py` (`TemplateRenderer` = Jinja with `StrictUndefined`; `LongImageRenderer` = Playwright capture with page-integrity validation, render semaphore, output pruning). `core/cache.py` `AsyncTTLCache` merges concurrent loads per key; the seven caches live on `ZmdLogsDataSource` and only the hot-bosses cache allows stale-on-error (plus the `hot-bosses.json` snapshot fallback). A TTL only decides whether a value may be *reused*, so entries are dropped once they can serve neither a fresh nor a stale read and the map is an LRU capped at `DEFAULT_MAX_ENTRIES` (256), `BATTLE_CACHE_MAX_ENTRIES` (64) for the two battle caches — a parsed battle carries its damage points and buff spans and measures 50–130 KB, so an uncapped map held tens of megabytes in a process that runs for weeks.

`main.py` also registers a `@filter.regex` handler that auto-expands ZMDLogs battle links in group chats (off by default, per-group/battle cooldown). All three reply paths — the `zmdlog` command, the quoted candidate pick and auto-expand — run through one error ladder, `main._run_guarded` (API error → route-specific wording; client error → 暂时不可用; `RenderError` → AstrBot fallback render, else 图片生成失败; anything else → generic + `logger.exception`), so they cannot drift apart again; it also reports whether the failure was *transient*, which only the auto-expand cooldown reads: the claim is released only when nothing useful was sent and a repost could plausibly do better (client error, 5xx, capture failure without fallback) — a dead link (404) and an image delivered through the fallback renderer keep it. Account lookups reached from any route go through `QueryService._render_account`, which answers a 404 in account terms regardless of which route kind caught it. Parse-layer `ValueError`s that are not `RouteParseError` get a short generic reply (defence in depth; `_parse_top` bounds its input before `int()`). Every config value is validated once at load by `core/settings.load_settings` (warn once, keep the default) so a typo like `65` cannot fail every keyword query, and a bad TTL, timeout or base URL cannot fail the plugin load or disable the renderer. `_event_origin` returns `""` when the platform gives no origin — callers decide what that means (watch routes refuse, the candidate store keys on it, auto-expand only dedupes).

**Rank watch (顶屁股通知).** `RankWatcher._loop` (`core/rank_watch.py`; `RankWatcher.start` is called from `initialize`, which runs on every plugin load — `on_astrbot_loaded` fires once per process and would miss a market install or a config-triggered reload — and `stop` from `terminate`) polls every watched account once per cycle through `ZmdLogsDataSource.get_account_rankings`: when the ranking index is complete, the account's rank on every board is the rank of its best row there (`ranking_index.account_rankings`, the same answer `users/{id}/rankings` gives), so a whole watch list costs **no request**; the endpoint answers only while the index is filling or for an account with no row anywhere. `find_rank_drops` skips a board absent from either side, so switching sources cannot invent a drop, and `_describe_drops` reads the board from the same index copy (`max_age=None`). Every request for one account stays inside the concurrency semaphore, and the board look-ups are capped at `MAX_DROPS_PER_NOTICE`. `core/watch.py` is pure. `find_rank_drops` reports only rank increases whose *previous* rank was inside `rank_watch_rank_threshold`, treats a board missing from the snapshot as a first sighting (never an event), and stays silent on improvements (a deliberate product decision). A baseline older than `max(3 × interval, 1h)` is discarded by `snapshot_is_usable` and re-seeded silently, so a restart after downtime does not replay everything that moved.

**Attribution is deliberately weak, and the wording must stay weak.** From one board read it is impossible to say who overtook the account: the row now at its *old* rank is usually a bystander pushed down by an insertion further up; a record posted in the window may be a player who was already ahead improving their own time; and `battleEndAt` is when the battle ended, not when it was uploaded, so a late upload can be the real cause while looking old. `find_new_record_above` therefore reports only what is provable — a record that is now ahead and postdates the previous check — takes its rank cutoff from the board response itself (not from the separately-cached account read), excludes the watched account, counts how many qualified, and returns `None` rather than guessing. The notice says 期间上方新增纪录, never 超过 TA 的是. Do not "improve" this into a causal claim without a real previous board state.

**Board watch (榜单新纪录).** `RankWatcher.run_board_cycle` runs after `run_account_cycle` in the same loop and reads `hot-bosses` **directly from the client**, never through the data source's cache or the on-disk snapshot: an *older* top list diffed against the baseline would report runs that merely fell out of the top as new. One request per cycle covers every watched board. `core/watch.find_top_run_changes` reports the battle ids now in the top that were absent from `board-snapshot.json` (`BoardSnapshot` keeps nickname / main C / duration per run, so the notice can also name who fell out — that displacement *is* provable, unlike an account overtake); a first sighting and a shrunken list (a deleted record) are never events, and `board_snapshot_is_usable` applies the same staleness bound with an empty top list counting as a real state. 关注 榜单 seeds the baseline from the cached cards, 取关 榜单 drops it once nobody watches the board, notices merge per chat via `join_board_notices`.

Ranks persist in `rank-snapshot.json` (payload v2: `{accounts: {id: {checkedAt, ranks}}}`); 关注 seeds a baseline when none exists (so the first notice needs one cycle, not two) and never overwrites one another chat is waiting on, 取关 drops it once nobody watches the account, an account the cycle could not reach keeps its previous ranks, and a failed write warns once. The same cycle feeds the 趋势 trace: `_poll_account` returns the full `PublicUserRankings` so the cycle can call `record_rankings`, `_seed_rank_snapshot` records the ranks held at 关注 time as the first points, `_forget_rank_snapshot` deletes the trace together with the baseline, and `rank-history.json` (v1: `{accounts: {id: {displayName, boards: {slug: {bossName, dungeonName, points: [[checkedAt, rank], …]}}}}}`) is only rewritten when a point was added or an account dropped. `core/timestamps.py` holds `utc_now_text` / `parse_timestamp` for all three modules (re-exported by `core/watchlist` and `core/watch` for existing imports). Notices are merged per chat per cycle (`join_rank_drop_notices`) because one new record demotes every watched account below it, and a burst of near-identical pushes is what gets a bot rate-limited. Delivery is `main._send_notice` (`context.send_message(origin, MessageChain([Plain(text)]))` under a timeout, treating `False` as failure), injected into the watcher as `notify` so tests capture it. **Both cycles deliver before the baseline moves** (`RankWatcher._deliver`): `notify` answers whether the chat received the text, and a cycle advances only the baselines whose message landed, so an unreachable chat makes the next cycle recompute the same change and try again instead of losing it for good (saving first and sending second is what lost it). `snapshot_is_usable` bounds the retry; the cost is that a key several chats watch can be announced twice when only one chat was unreachable. 关注 列表 and 取关 keep working when `rank_watch_enabled` is off; only adding is refused. The cycle merges its results onto the live snapshot map and re-checks the watch list before sending, because 关注 / 取关 can run while it is awaiting — installing the map it started from would drop a baseline just seeded and notify a chat that has since unfollowed. The two text-only route families (别名 / 关注) are wrapped in their own error guard: they never reach `QueryService.dispatch`, so without it an unexpected error would surface as a traceback.

## Invariants to preserve

- **DPS only.** Never send `metric`, never show RDPS rankings; `parse_boss_ranking` rejects `metric != "dps"`.
- **Every board ranking is read through `core/ranking_index.RankingIndex`** (owned by `ZmdLogsDataSource.ranking_index`; `get_boss_ranking(slug, max_age=)` delegates to it, default `max_age` = `ranking_cache_ttl_seconds`, `None` = whatever the index holds). It keeps all ~49 rankings resident (1871 rows / 2.4 MB JSON, ~5 MB parsed; a cold fill is ~13 s at concurrency 4) because upstream has no per-character query and 角色排名 / the account watch need every board. Three freshness drivers: a round-robin re-read of the oldest board every `ranking_index_pace_seconds` (20 s, min 5, so a full pass ≈ 16 min); every 60 s a fresh hot-bosses read (`refresh_hot_bosses`, which also `put`s it into the hot-bosses cache fresh for `signal_period_seconds` + 5 s — the loop checks the signal clock once per pace, so the next read can land pace seconds late, and a shorter freshness left a gap in which a keyword query paid the 4 s cold read after all) whose top-three battle ids are diffed against the held rows (`apply_signal`; a card shorter than three with more rows held means a deletion) and any changed board is re-read at once; and a reader asking for a fresher copy than held, which fetches and updates the index. A failed refresh serves the held copy for up to `STALE_FALLBACK_MAX_AGE_SECONDS` (30 min) with a warning, then raises; background failures log once per streak. `ranking_index_enabled=false` disables the loop only: reads stay on-demand through the same `get`. Started by `ZmdLogsDataSource.start()` from `initialize` / `on_astrbot_loaded`, stopped by `close()`.
- **The LLM tool surface is 图文并茂, and the picture is the authority.** `main.py` registers **four** `@filter.llm_tool` handlers over `core/toolbox.ToolService` (resolution + rendering) and `core/facts.py` (the text) — one per subject (榜单 / 战报 / 角色 / 账号), never one per feature, a rule the user set on 2026-09-05 when a seven-tool surface was cut: AstrBot sends every active tool's schema with every LLM request (seven cost ≈1445 tokens on every message in every group) and a model choosing among overlapping tools picks the wrong one, so a new view of a subject becomes a parameter or extra lines in that tool's text (team counts and a character's partners live in the board tool's text, 对比 is the battle tool's `compare_with`). Each draws the page zmdlog would have drawn, sends it with `event.send` **from a background task** (`main._spawn` / `_send_tool_image`, cancelled at terminate) so the text reaches the model at once and the platform upload overlaps the model's second round trip instead of preceding it, and returns the facts behind it as text — **at most one picture per turn** (`_TOOL_IMAGE_SENT` on the event, set before the task starts), because a model answering one question calls two or three tools and three long images is spam. The battle tool reads detail, export and suit catalog with one `gather`, like the command path. Every docstring says 图里有完整数值，你不要复述数字，只解读: a model that retypes a figure eventually drops a digit, and the rendered number never passes through it. Two rules bind `facts.py`: return **computed** facts, never a raw array (a six-minute battle carries 1868 telemetry events), and report plainly when the data does not cover the question. Tools answer **what the public records contain** and never which character or team is better — the leaderboard is a self-selected sample of successful speed runs by stronger players, so a cross-run comparison measures the players as much as the subject; 循环 DPS and 专武收益 need a damage calculator and belong to `astrbot_plugin_zmdlore`, not here. `ToolService` also refuses a below-threshold fuzzy board match that a command would have rendered anyway: a command has a reader in the loop to judge the page, a tool call does not.
- **Rendering is gated twice.** `LongImageRenderer._capture` caps concurrent captures at `DEFAULT_MAX_CONCURRENT_RENDERS` (2) *and* the callers waiting for a slot at `DEFAULT_MAX_QUEUED_RENDERS` (8), with the wait itself under `render_timeout_ms`; only the wait is timed, because wrapping the capture would trip on a legitimately slow page. An overloaded bot answers 图片生成失败 while the reply is still worth having.
- **Image-only output, with two carve-outs.** Rank-watch notices and the 关注 / 取关 / 别名 replies are plain text: they are configuration actions and pushes, not query results. The LLM tools are the second: they send the picture *and* return text, because the text is what the model reasons over. Any query/help result is one PNG; render failure returns a short error text, never a text fallback of the data. `_require_renderer()` raises `RenderError` if Playwright setup failed. When only the Chromium capture fails, `RenderError.html` carries the rendered page and `main._render_with_astrbot` retries through AstrBot's `html_render` (config `fallback_to_astrbot_renderer`, on by default) after neutralising Jinja delimiters.
- **Top-3 pages must not leak ranking-only fields** (slug, percentile, DPS, roster, links) — enforced by `test_top_three_template_does_not_leak_ranking_fields`.
- **User-facing errors are short and generic**; log only exception type / API code, never response bodies or stacks.
- **Strict for typed fields, lenient for untyped ones — and lenient for optional telemetry.** `models.py` validates every field the upstream Pydantic schema types; the two lists it leaves as bare dicts (`equips[].stats`, `equips[].enhanceLevels`) are read by `_parse_equip_stats` / `_parse_enhance_levels`, which keep well-formed entries and drop the rest, so one odd gear line can never fail a battle that used to render. `timelineEvents` and `characterStates` are typed upstream but read the same lenient way (`_parse_damage_points` / `_parse_character_state_buffs`, entry by entry, anything unreadable skipped): they only feed the DPS curve and the buff band, two sections the card must render without. Raw item ids are never printed as names (`is_raw_item_name` → 名称未收录); a raw buff key prints its effect instead of the key.
- **Help data (`core/help.py`) must be updated whenever a user-facing command changes**; `test_routing_help` asserts the exact command list. Every `HelpCommand` carries an `answers` line — the question that command answers, ending in `？` (asserted by the same test) — because 阵容 / 角色统计 / `--角色` are indistinguishable from their syntax alone; sections are grouped by what the reader wants to know and each carries a one-line `summary`. Version comes from `metadata.yaml`, don't hardcode.
- `core/presentation/` is a package, one module per page family (`common`, `boards`, `statistics`, `account`, `charts`, `rail`, `battle`, `trend`, `compare`) whose `__init__` re-exports every builder and view model, so callers import from `core.presentation` as before; the dependency direction is common ← charts ← rail ← battle ← compare, never back.
- Rendered pages must contain `#zmd-page > .main-panel` and the local background data-URL (`resources/common/scene-background.svg`, inlined as `data:image/svg+xml`), or `_validate_page` fails the render. Templates extend `resources/common/base.html`; page-specific CSS is `{% include %}`d into `extra_styles`. Decorative elements that overflow must live inside `.scene-deco` (overflow hidden) or `#zmd-page` scrollWidth exceeds 1280 and validation fails.
- **Visual language is Endfield-style** (light paper `#f1f1ee`, ink `#1c1c1c`, accent yellow `#f8d34d`, cut corners via `clip-path`, skewed badges, Barlow for Latin/digits, MiSans for CJK). Fonts are subset woff2 files (CJK = full GB2312, 6763 chars) in `resources/common/fonts/`, read once by `core/render._load_fonts`. Chromium gets them *linked* on the reserved origin `render.FONT_ORIGIN` (`https://fonts.zmdlog.invalid`) and the route handler serves the bytes from memory — embedding them as data URLs made every document 3.7 MB and cost a third of each capture; the copy attached to a `RenderError` for the AstrBot fallback embeds them (`TemplateRenderer.render_*(embed_fonts=True)`), because that renderer cannot reach the route handler; regenerate with `tools/build_fonts.py <dir-with-source-ttfs>` (needs fonttools+brotli, see `resources/common/ASSETS.md`). No AGPL assets remain.
- Avatar URLs from upstream are site-relative; every page builder takes `web_base_url` and resolves via `_safe_asset_url` (unsafe schemes → `None`). `core/identifiers` compares origins with default ports normalised (`https://host:443` ≡ `https://host`) and treats a malformed port (`:abc`, `:99999`) — in the link *or* in the configured `web_base_url` — as "not a trusted link", never as a raised `ValueError`.
- `hot-bosses` is the sole source of the board/dungeon index — no hardcoded board catalog; a JSON snapshot of the last good payload is kept in the data dir (`hot-bosses.json`) and used when upstream is unreachable. Matching derives aliases automatically (`derived_board_aliases`: strip `·苦难/·残酷` suffix and `{dungeon}·` prefix; `derived_dungeon_aliases`: split `影拓丰碑4期 · 山中见犼` into parts + `丰碑4/影拓4`) and pinyin keys (`pypinyin`, full + initials, `MatchLevel.PINYIN_EXACT`; a CJK query is also compared by its own full pinyin so homophone typos like 躁雷→噪雷 hit as PINYIN_EXACT 0.98 / PREFIX_SUFFIX 0.85). A single below-threshold similarity hit renders directly; only ≥2 weak hits become a pick list. An exact hit on several dungeons of one phase becomes a DUNGEON_SCOPE instead of AMBIGUOUS; an exact hit on a one-board dungeon is promoted to that board. Hand-written aliases live in `aliases.json` (`boards` keyed by `bossSlug`, `dungeons` keyed by full `dungeonName`); the bundled file only seeds `data/plugin_data/astrbot_plugin_zmdlog/aliases.json`, which is the editable copy.
- Only image requests to `api_base_url` / `web_base_url` origins are allowed during capture; everything else is aborted. The Playwright route handler only ever sees the first hop of a redirect chain, so allowed image requests are fetched *inside* the handler (`route.fetch(max_redirects=0)`) and any 3xx is aborted; 200-responses are kept in `render.AssetCache` (in-memory, 30-day TTL, 32MB total / 2MB per item, insertion-order eviction — icons are static files addressed by path, so the byte caps bound the cache, not the clock) because every capture runs in a fresh incognito context and would otherwise re-download the whole static avatar catalog per render — otherwise a redirect served by an allowed origin would pull the image from anywhere. This has no unit test (needs Chromium); verify with a two-local-origins script when touching `_route_asset_request`.

## Config

`_conf_schema.json` is the AstrBot config schema; `core/settings.py` (`PluginSettings` / `load_settings`) reads it once at load, replacing every unusable value by its default with one warning, and `tests/test_settings.py` asserts the dataclass defaults equal the schema defaults key for key. `README.md` documents commands/config for end users and must be updated alongside. Rendered PNGs go to `StarTools.get_data_dir("astrbot_plugin_zmdlog")/render` (falls back to system temp when StarTools is unavailable); `@filter.on_astrbot_loaded` warms up Chromium. `_HIGH_DPI_PAGE_KINDS` in `render.py` (help, ranking, account, battle, character-stats, character-boss, roster, loadout, skills, trend, timeline, compare) are captured at `device_scale_factor=2`; every `LongImageRenderer.render_*` is built by `render._captured(page_kind, TemplateRenderer.render_*)` and `_render` owns the template error and the fallback copy (PNG 2560px wide); the long top-3 pages stay 1x. `metadata.yaml` carries `short_desc`; `logo.png` (256×256) is the market icon.

## Upstream facts (verified against endfield-suite-open `apps/api/app/services/public_data.py`)

- `characterAvatarUrl` / `avatarUrl` in hot-bosses, rankings and battles are usually **site-relative paths** (`/images/...`), occasionally absolute CDN URLs — resolve them against `web_base_url` before rendering.
- In battle detail every `roster[].accountDisplayName` is the uploader nickname, so `roster[0]` is a valid uploader name source; `GET /api/battles/{id}/share-summary` also returns `uploaderNickname` directly.
- Battle detail `roster[]` carries the loadout recorded at upload: `slot` (1-based), `characterElement` (`physical|fire|cryst|natural|pulse` = 物理/灼热/寒冷/自然/电磁), `characterLevel`, `characterPotential`, `weapon{weaponName, weaponLevel (often null/0), weaponRefine, iconUrl, skills[{skillKey, level, potentialLevel}]}` where `sk_wpn_*` is the weapon's own skill and `wpn_attr_*` / `wpn_sp_attr_*` are affixes, `equips[]` (4 pieces: 护手 / 护甲 / 配件 ×2; `pieceName` falls back to the raw `item_equip_…` id with `suitName` null when the catalog has no name; **`suitName` is not a property of the item and must never be used as an identity or as the truth**: surveyed over 270 battles, 17 of 129 item ids come back under more than one suit, `item_equip_t4_suit_usp02_body_03` alone under eight, and 26 times the same item id disagreed with itself on two characters of the *same* battle; `item_equip_t4_suit_spellburst_hand_01` was once labelled 长息, which is the name of `suit_usp02`. Compare and group gear by `itemId`, take the suit name from the game data catalog, and treat `suitName` as a fallback label only. `独立装备` is what upstream calls a `_parts_` piece, which belongs to no suit; `enhanceLevels[{index, level}]`; `stats[{slot: main|sub1..3, name, value, level}]` with ratio stats as fractions, e.g. 0.1495, and occasionally untranslated names `Main` / `副能力`), and `skills[{skillKey, level}]` (`_attack1..5`, `_normal_skill`, `_combo_skill`, `_ultimate_skill`, talents at level 1). Older uploads (crisis-contract era, parser < v34) have empty weapon skills / stats / enhance lists. `roleSkillStats[]` (`characterName, skillKey, skillName, castCount, totalDamage, avgDamage, maxDamage`) is per damage source: the normal attack chain is one row per segment, `skillName` may be a raw key or English placeholder (`burning status`, `poise can be breaking attacked`), and `buff_common_*` rows are engine-side damage (element reactions, statuses). `timelineEvents[]` (`tsMsFromStart`, `laneType: skill|buff`, `sourceCharacterName`, `value`, `durationMs`, `effects[{zone, element, rate}]`, `poiseDamage{value, current_value}`, …) is the per-hit log: 171 events / 0.2 MB for a 22 s run, 1868 / 1.9 MB for a six-minute one, parsed in ~12 ms. Its damage values sum **exactly** to `battle.totalDamage`, and per `sourceCharacterName` to each `participants[].totalDamage`, which is what makes the DPS curve reconcile with the table above it. `characterStates[]` (`characterName`, `loadout`, `initialBaseline`, `buffsReceived|buffsGiven|debuffsApplied[{eventKey, eventName, sourceCharacterName, targetCharacterName, startTsMsFromStart, durationMs, effects}]`) is the same buff data pre-grouped per character, and is the source the buff band uses. `poiseDamage` (失衡) is present but deliberately **not** drawn: speed runs sample it a handful of times and never break it, there is no cap field (upstream's 上限 is the max observed), so the lane would be a flat line on exactly the fights people look at.
- `GET /api/battles/users/{id}/rankings` lists the account's best record on **every** board it ever uploaded to, including boards absent from hot-bosses (retired or non-standard content: `indie_hard014`, `dung01-takestwo004`, `dung01-group-gold01`, `dung-group-ss01`, `unknown-dungeon` …). On the boards both carry, its `rank` equals the rank of the account's best row in that board's ranking — verified on 8 accounts on 2026-09-06 with zero differences — which is what lets the rank watch read ranks off the index. The index (and therefore the watch and the 趋势 trace from then on) covers the hot-bosses boards only, the same universe every other feature already lives in.
- Board slugs come from static `BOSS_SEEDS`; the crisis-contract board is `indie_group_ccdg` (`bossName` 破潮之像, `dungeonName` 危机合约). Unknown slug → 404 `boss_not_found`.
- `GET /api/characters/{character_key}/boss-statistics` (same `range`/`potential`/`metric` params) returns one character's row for **every** statistics board (zero-sample rows included; crisis contract and inactive season towers excluded); each row equals the character's row in the matching per-board response, plus `rankedCharacterCount`. Unknown key → 404 `character_not_found`. Admin operator is unified as `chr_9000_endmin`.
- `GET /api/bosses[/{slug}]/character-statistics` (`range=7d|14d|30d|all`, `potential=0|1-5|all`, `metric` defaults to dps) returns every six-star character (`SIX_STAR_STATISTICS_CATALOG`), zero-sample rows included; `rank` is null when `normalSampleCount < minimumSampleCount` (5); whiskers are min/max of IQR-filtered normal samples, `maximum` includes outliers. Crisis contract → 404 `character_statistics_not_available`. `professionGroups[].entries[].usagePercent` is the share within that profession slot over **all** rows.
- `GET /api/v1/battles/{battle_id}/export` (public, no token, per-IP 60 requests/min → 429 `rate_limited`, `Cache-Control: max-age=60` + weak ETag, CORS `*`; the read-only contract upstream keeps for external axis tools) returns `{schemaVersion: 1, battleId, parserVersion, rulesVersion, dungeon{dungeonSlug, dungeonName, bossKey, bossName}, durationMs, battleStartAt, battleEndAt, roster[…], casts[…]}`. `roster` is the detail roster minus profession / avatar / element / accountDisplayName; `casts[]` = `{tsMsFromStart, endMsFromStart|null, characterKey, skillKey, skillName, skillSource: "unknown"|"Summon", recoversEnergy}` and includes normal-attack segments and summoned entities' casts; `tsMsFromStart` can be negative (before the timer), `endMsFromStart` null or past `durationMs`, 10–110 casts per speed run. 404 for a non-public battle, 422 `battle_export_unsupported` for uploads older than parser v33 (no casts; the crisis-contract era). The web's per-hit `timelineEvents` in the detail response (1.6 MB for a six-minute fight) is *not* used for the timeline.
- `GET /api/game-data/equip` (public, no auth, static game data) returns `{kind, count, entries[{suitID, name, displayName, rarity, pieceCount, icon, passiveSkillId, …}]}` — roughly two dozen suits, the authority on which suit an item id belongs to. `suit_none` carries its own id as its `name` and is skipped. Sibling modules `character` (33), `weapon` (79), `enemy` (92), `dungeon` (94), `buff`, `skill`, `attribute_type` exist on the same router; the detail routes (`/api/game-data/{kind}/{id}`) answer 503 `catalog_data_missing`. `GET /api/game-semantics/*` and `/api/game-semantics/hints/*` are live too but **not worth using**: their ids are internal `abilityentity_*` keys with mostly empty `decodedName`, they do not match the `roleSkillStats` keys the plugin prints, and `attribute_type` is English enum names (`MaxHp`, `AttributeType11`) rather than the Chinese labels the battle payload already carries.
- `GET /api/battles/users/search?query=&limit=` (public, no auth): NFKC-normalized case-insensitive substring match over public nicknames; `query` must be 2–64 chars after strip (else 422), `limit` 1–20 (default 10); returns `{query, hasMore, accounts[{accountId, accountDisplayName}]}`, only accounts with valid public ranking records. Server caches ≤60s, HTTP `max-age=30`. Full contract in local `PUBLIC_ACCOUNT_SEARCH_API.md`-style doc (Downloads).
